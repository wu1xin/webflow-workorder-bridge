# 放行边沿自动回灌空档 设计文档

> 编写日期：2026-07-13
> 关联：

> - `docs/plans/2026-07-10-SSE群生命周期实时同步-design.md`（§4/§7 已把本缺口记为「不回补」的既有取舍）

## 1. 背景与目标

群名来回变化 → 同一个群（`conversationId`/sessionId 稳定，改名不变）在下游「按名裁决」下反复 **放行(1) ↔ 不放行(0)**。

**不放行期间**消息一条都不落库，因为三层拦截：

1. SSE 实时链路对非放行群**连 REST 都不发**（`ingestRealtime`，[syncService.ts:463-464](../../server/src/sync/syncService.ts#L463-L464)）。
2. 落库核再兜一道：非放行群一律 `skipped`（`ingestOne`，[syncService.ts:388](../../server/src/sync/syncService.ts#L388)）。
3. 该 skip 发生在 dedup **之前**（[:391](../../server/src/sync/syncService.ts#L391)）——这些消息从没在 dedup 留痕，是后面「能补回」的伏笔。

**改回放行后**：实时只从当下往后；补偿同步 `runCompensation` 从**全局水位** `last_sync_timestamp` 起拉（[channelState.ts:87-92](../../server/src/db/channelState.ts#L87-L92)），而该水位是按 channel 全局、单调只增的——生产里其他放行群早已把它推过空档 → 补偿从空档之后起拉 → **空档永久丢失**。

**业务语义（已确认）**：不放行 = 「下游暂时没把这个群纳入转发范围」，期间聊天记录对工单/客服**有价值，应补齐**。这不是合规红线，横跳丢消息是需要修的缺口。

**目标**：放行 `0→1` 边沿**全自动**触发单群定向回拉，把该群「已入队水位（无记录则 0）→ 现在」的空档补进 queue。首次开通老群（queue 无记录）从 0 全量拉。

## 2. 现状与缺口

见 §1 的三层拦截。缺口本质：**放行是会话级、单调只增的全局水位却是 channel 级**——二者错配，导致「群从不放行翻回放行」这一事件无人认领去补它自己的空档。

现有唯一补救是手动「强制全量重拉」`triggerFullSync`（对所有放行群 start=0），代价大且需人工。本设计把「补空档」这件事**收窄到单群、由放行边沿自动触发**。

## 3. 设计

### 3.1 核心机制：放行边沿触发单群定向回拉，复用现有链路

「回灌」与「SSE 实时回查」本质是同一个动作——给定 `(群, 起点)` 定向拉 REST 入队，区别只在起点。现有 `scheduleRealtimePull(talker, start) → drainRealtimeLoop → pullRealtime → ingestOne` 这条链已具备全部所需能力：单群、从 `start`、**按 talker 合并防抖**（每群唯一在途循环）、错误隔离、成员/头像回补、**不碰全局水位**。

因此回灌直接搭车：边沿放行时对该群调 `scheduleRealtimePull(talker, start)`。

**对比备选**（YAGNI 淘汰）：另建「不放行也落库、压着不转发」的暂存缓冲——要改落库核语义 + 新状态，且未知新群启发式会把海量陌生群消息全缓存（存储/REST 放大），违背「只补会开通的群」的意图。否决。

### 3.2 起点统一公式

```
start = MAX(msg_timestamp of queue WHERE channelId=? AND conversationId=该群) ?? 0
```

- 用 `MAX` **本身（含）** 而非 `MAX+1`：秒级时间戳同秒可能多条，含边界靠 dedup 挡重、绝不漏。
- 横跳过的群 → 有水位 → 只补空档。
- 首次开通的老群 → queue 无记录 → `0` → 从头全量（符合目标）。

依据「queue 转发后不删行、仅 `status` 流转」（[queue.ts:299-317](../../server/src/db/queue.ts#L299-L317)），按群水位可直接从 queue 推导，**不新增水位列**。

### 3.3 边沿检测：在唯一翻转点

`push_allowed` 只有 [`chatGroup.markSynced`](../../server/src/db/chatGroup.ts#L102-L110) 会翻转（`markSyncFailed` 保持原值 → 下游失败绝不误触发回灌）。改动：`markSynced` 在事务内对每行**先读旧值、再 set 新值**，收集并返回本轮 `0→1` 的 `conversationId` 列表（签名 `void → string[]`）。DB 层天然知旧值，无竞态。

### 3.4 边沿回传：经 syncAll 透出

[`groupSyncService.syncAll`](../../server/src/sync/groupSyncService.ts#L57-L86) 的 `.then` 里拿到 `markSynced` 返回，作为 `syncAll` 结果透出（`Promise<void> → Promise<string[]>`，下游失败/无群返回 `[]`）。**不给 GroupSyncService 注入回调**——保持它「纯算裁决」、不反向依赖拉取能力。

### 3.5 回灌收口：SyncService 一个私有方法 + 按调用点接线

新增私有 `backfillNewlyAllowed(convIds)`：对每个群算 `start`（queue 水位 ?? 0）→ `scheduleRealtimePull(talker, start)`。

各 `syncAll` 调用点接线：

| 调用点 | 是否回灌 | 原因 |
|---|---|---|
| `runFullSync` | ❌ | start=0 已把所有放行群全量拉过，边沿群在其中，回灌重复 |
| `runCompensation` | ✅ | 边沿群**从主循环 candidates 排除**、只由 backfill 从各自旧水位/0 补（见 §4：否则主循环先从全局水位拉边沿群会顶高其 queue 水位，使 backfill 失效） |
| `syncGroupsNow`（手动同步群） | ✅ | 手动同步可能翻转边沿 |
| `onGroupRenamed`（改名，核心横跳场景） | ✅ | |
| `onNewGroup`（新入群/首次开通） | ✅ | start=0 → 全量，符合「首次开通老群全量」 |

私有包装 `syncGroups(sessions)`（runFullSync/runCompensation 共用）同样透出 newlyAllowed：`runFullSync` 忽略、`runCompensation` 接住调 backfill。

### 3.6 路径复用 `sse`，不新增 `backfill` 枚举

回灌走 `scheduleRealtimePull`，而它**按 talker 合并**在途循环——边沿那一刻同群的实时 SSE 很可能也在触发，两者取 `min(start)` 合并成一轮拉回。这批 REST 消息是同一批，硬拆成两种 `ingest_path` 反而要放弃合并、还得处理同群并发。故回灌**沿用 `ingest_path='sse'`**（理解为「定向回拉」，回灌本就是定向回拉）。排障靠 `msg_timestamp` 远早于 `created_at` 辨认，够用。零新枚举、零迁移。

### 3.7 可 await 与错误传播（SSE 旁路改造）

现有 SSE 旁路 `onNewGroup` / `onGroupRenamed` 是 `void this.groupSync.syncAll(...)` fire-and-forget。接了 backfill 后，若仍 `void`，则「空档补回」既测不到、错误也传不出。改造：

- `onNewGroup` / `onGroupRenamed` **返回 Promise**：同步建行（`upsertSeen`，防抖前提不变）后 `return syncAll(...).then(newlyAllowed => this.backfillNewlyAllowed(newlyAllowed))`。
- `detectGroupLifecycle` 返回该 Promise；`ingestRealtime` 把它与 `scheduleRealtimePull`（放行群那条）**合并**返回：非放行群返回 lifecycle Promise，放行群返回 `Promise.all([lifecycle, pull])`。测试 `await ingestRealtime(...)` 即可等到「重裁 → 翻放行 → 回灌入队」全链。
- **同步流程**（`runCompensation` / `syncGroupsNow`）本就在 async/Promise 链内，`await`（或 `.then`）拿到 `syncGroups` 透出的 newlyAllowed 后触发 `backfillNewlyAllowed`。
- `dispatchSystemEvent`（放行群 REST 改名路径）调 `onGroupRenamed`：放行群已是 1，重裁不产生 `0→1` 边沿 → newlyAllowed 恒不含它 → backfill 空跑、无害，保持 `void` 调用即可。

**连带**：`syncAll` 桩（测试 `noopGroupSync` / `spyGroupSync`）返回值由 `Promise.resolve()` 改为 `Promise.resolve([])`，`backfillNewlyAllowed` 对空列表 no-op（`convIds.length === 0` 早返回），双保险。

## 4. 边界 / 幂等 / 并发

| 情形 | 行为 |
|---|---|
| 反复横跳 | 每次 `0→1` 从该群当前 queue 水位补，补完水位前进、下次续；快速横跳被 `scheduleRealtimePull` 合并成一轮。不重、不漏、收敛 |
| 回拉中途又转不放行 | 后半段 `ingestOne` 闸门开始 skip、水位停在中间，下次放行再续拉，收敛 |
| compensation 主循环 vs 边沿群 backfill | 边沿群已从主循环 candidates 排除（`!newlySet.has(...)`），只由 backfill 从各自旧水位/0 补。**必须排除**：`allowedGroupSessions` 在 `syncGroups` 提交后读、边沿群此时已放行会被纳入 candidates，主循环从全局水位拉它会把其 queue 水位顶到 now，随后 backfill 读到被顶高的水位、漏掉水位以下空档（这正是本 feature 要解决的问题）。非边沿的老放行群仍走主循环从全局水位补，二者不重叠、无冗余 REST |
| 下游 / DB 异常 | `syncAll` 内部自吞（`markSyncFailed`、不翻转、告警）→ newlyAllowed=`[]` → 不回灌 |
| 未配 `groupSync` | 无裁决、无边沿、无回灌，保持现状 |
| 群从没入过队（首次开通老群） | 水位查询返回 null → start=0 → 全量回拉 |

## 5. 测试（vitest，内存库 + 注桩）

- `chatGroup.markSynced` 边沿：未放行→放行算边沿；已放行→放行、放行→不放行不算；`markSyncFailed` 不产生边沿。
- `queue.maxTimestampForConversation`：有记录取 max、无记录返回 null、跨会话隔离。
- `groupSyncService.syncAll` 返回 newlyAllowed；下游失败返回 `[]`。
- `SyncService.backfillNewlyAllowed`：边沿群按 queue 水位算 start 调 `scheduleRealtimePull`；无水位群 start=0；空列表 no-op。
- 端到端横跳：放行→有消息入队→改名转不放行（闸门 skip）→改回放行→backfill 从水位补回空档消息入队；二次横跳只补新空档、不重。
- 首次开通老群（queue 无记录）→ backfill start=0 全量。
- `runFullSync` **不**触发 backfill（避免重复）。

## 6. 未尽事项 / 遗留风险

- **queue 归档假设**：按群水位靠「queue 不删行」推导。若将来引入归档/清理，水位会回退 → 重复回灌（dedup 兜底但放大 REST）。届时改为 `chat_group` 独立持久化水位列即可。现状 queue 只做 status 流转、不删行，本期不引入新列（YAGNI）。
- **REST 历史保留有限**：首次开通老群从 0 全量，只能拉到 WeFlow 侧还保留的部分——外部约束，与现有 `runFullSync` 相同，非本方案能解。
- **「撤销放行」（1→0）** 的在途处理不在本期：现有闸门已在 `ingestOne` 处丢弃非放行群消息，无需额外动作。
