# 群消息清空重拉同步 设计文档

> 编写日期：2026-07-15
> 定位：**开发/测试期**用来重置单个群（或全部群）同步状态的内部工具（内部工具，优先简单）。
> 关联：
> - `server/src/sync/syncService.ts`（复用 `scheduleRealtimePull` 单群定向重拉 / `triggerFullSync` 全量 / `progress.running` 防并发）
> - `server/src/db/queue.ts`（按群/按 channel 删；`external_id` 即 dedup_key）
> - `server/src/db/dedup.ts`（`(channel_id, dedup_key)`，无会话维度）
> - `server/src/db/channelState.ts`（全局水位 `last_sync_timestamp` / 投递断点 `breakpoint_timestamp`）
> - `server/src/db/database.ts`（`Db` 门面，持 `raw` 连接、跨表事务）
> - `server/src/routes/groups.ts` / `web/src/pages/weflow/GroupsPage.vue`（触发入口）

## 1. 背景与目标

开发/测试期需要反复把某个群的同步状态**清干净、从头重拉一遍**，用来验证拉取入库与下游转发链路。

现有的「强制全量重拉」`triggerFullSync`（`POST /api/sync/full`）靠 dedup 兜底幂等——**已入库的消息不会真的重入**。因此它能补缺、却不能"重灌"。测试时想看一条消息**完整重跑一遍**（重新拉取 → 重新入队 → 下游重新投递），必须先真正**清空**该群的本地痕迹，才能绕过 dedup 重新拉回。

**目标**：
- **单群**：删该群 `queue` 行 + 对应 `dedup` 痕迹，从 0 定向重拉。保留 `push_allowed` 裁决、不碰全局水位。
- **全量**：清空本 channel 整张 `queue` + 整张 `dedup` + 重置全局水位/断点，再触发全量重拉（dedup 已空 → 真重灌）。
- 入口：群列表页每行一个「清空重拉」操作 + 顶部一个「全部清空重拉」按钮。

**已确认取舍**：
- 下游重投是**预期行为**——清空重拉 = 完整重跑链路（拉取 + 转发），不做去重/暂停 forwarder 的特殊处理。
- 单群**保留** `push_allowed`：只清消息数据，不动放行裁决、不动全局水位（未放行群本就无 queue 行，重拉被闸门 skip，reset 对其为无害空操作）。

## 2. 关键数据关系

- **`dedup_key = external_id`**：adapter 归一化时 `dedupKey = externalId = String(serverId ?? localId)`（[adapter.ts:23-25](../../server/src/weflow/adapter.ts#L23-L25)），而 queue 行存了 `external_id`。故 `queue.external_id` 与 `dedup.dedup_key` 对同一条消息**等值**——可由 queue 按群反查出该群的 dedup 键。
- **撤回键**：撤回事件另用 `revoke:${serverId}` 作 dedup 键（[syncService.ts:670](../../server/src/sync/syncService.ts#L670)）。按群清 dedup 时须一并清 `'revoke:'||external_id` 变体。
- **dedup 表无会话维度**（主键 `(channel_id, dedup_key)`，[schema.ts:32-37](../../server/src/db/schema.ts#L32-L37)），所以"按群清 dedup"只能靠 `queue.external_id` 反查，**顺序上必须先删 dedup 再删 queue**（删了 queue 就丢了反查依据）。
- **放行群的 dedup 与 queue 一一对应**：非放行群在 `ingestOne` 于 dedup **之前**就被闸门 skip（[syncService.ts:394-397](../../server/src/sync/syncService.ts#L394-L400)），从不进 dedup 也不进 queue。故对放行群，凡进过 dedup 的消息都有对应 queue 行（重复命中的原件也在 queue），由 `queue.external_id` 反查得到的键集**恰好**覆盖该群 dedup 足迹。

## 3. 设计

### 3.1 复用现成链路

「单群从 0 重拉」= `scheduleRealtimePull(conversationId, 0)`。该链（[syncService.ts:526](../../server/src/sync/syncService.ts#L526) `scheduleRealtimePull → drainRealtimeLoop → pullRealtime → ingestOne`）本就具备：单群、从 `start`、按 talker 合并防抖、走 `ingestOne` **尊重放行闸门**、错误自吞进日志、**不碰全局水位**——正是所需。放行边沿回灌 `backfillNewlyAllowed` 已在用它。

「全量重拉」= `triggerFullSync`（[syncService.ts:178](../../server/src/sync/syncService.ts#L178)）。清空 dedup 后再触发，即可绕过幂等真重灌。

### 3.2 数据层（新增方法）

`QueueStore`：
- `deleteByConversation(channelId, conversationId): number` — `DELETE FROM queue WHERE channel_id=? AND conversation_id=?`，返回删除行数。
- `deleteByChannel(channelId): number` — 清本 channel 全部 queue。

`DedupStore`：
- `deleteByChannel(channelId): number` — 清本 channel 全部 dedup。

`ChannelStateStore`：
- `resetWatermark(channelId): void` — 把 `last_sync_timestamp/rawid`、`breakpoint_timestamp/rawid` 置 NULL。**保留 `install_time`**（否则会被误判成首装、语义漂移）。

### 3.3 跨表编排（`Db` 门面）

跨表事务放在 `Db`（`database.ts`，持 `raw` 连接、天然知两表，符合"调用方不直接碰 SQL"的现有分层）：

```
resetConversation(channelId, conversationId): { queue: number, dedup: number }
```
一个 `raw.transaction`，**先删 dedup 后删 queue**：
```sql
DELETE FROM dedup WHERE channel_id=@ch AND dedup_key IN (
  SELECT external_id            FROM queue WHERE channel_id=@ch AND conversation_id=@conv AND external_id IS NOT NULL
  UNION
  SELECT 'revoke:'||external_id FROM queue WHERE channel_id=@ch AND conversation_id=@conv AND external_id IS NOT NULL
);
DELETE FROM queue WHERE channel_id=@ch AND conversation_id=@conv;
```

```
resetChannel(channelId): { queue: number, dedup: number }
```
一个事务：`queue.deleteByChannel` + `dedup.deleteByChannel` + `channelState.resetWatermark`。

### 3.4 SyncService 编排（新增两个公开方法）

遵循项目异步风格（直接 `return` Promise 链 / fire-and-forget 复用现有语义）：

```
resetGroup(conversationId): { accepted, status }
  progress.running          → { accepted: false, status }   // 防与全量/补偿同步竞态
  否则 → db.resetConversation(CH, conversationId)
       → void scheduleRealtimePull(conversationId, 0)        // fire-and-forget，不等重拉完成
       → { accepted: true, status }
```

```
resetAllAndFullSync(): { accepted, status }
  progress.running          → { accepted: false, status }
  否则 → db.resetChannel(CH)                                 // 清 queue+dedup+水位
       → void runFullSync()                                  // dedup 已空 → 真重灌
       → { accepted: true, status }
```

### 3.5 路由（`groups.ts`，语义归属群管理）

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/weflow/groups/:conversationId/reset` | 单群清空重拉 |
| `POST` | `/api/weflow/groups/reset-all` | 全部清空重拉 |

`accepted=false` → `409 + status`，与 `/api/sync/full`（[sync.ts:14-21](../../server/src/routes/sync.ts#L14-L21)）一致。群 ID 走 path 参数（Fastify 自动解码 `@chatroom` 等字符）。

### 3.6 前端（`GroupsPage.vue`）

- `web/src/api/groups.ts` 加 `resetGroup(conversationId)` / `resetAllGroups()`。
- 表格新增末列「操作」：每行 `ElButton type="danger" size="small"`「清空重拉」→ `ElMessageBox.confirm`（点名群名 + 提示下游会重收）→ `resetGroup` → `ElMessage.success` → `load()` 刷新。单行 loading 用 `resettingId` ref。
- 顶部工具栏「立即同步群」旁加 `ElButton type="danger"`「全部清空重拉」→ 强 `confirm({ type: 'warning' })`（"清空所有群、不可撤销"）→ `resetAllGroups` → 刷新。
- 命中 409（`ApiError`）→ 提示"已有同步在进行中，请稍后重试"。
- 复用现有 `ApiError` / `ElMessage` / loading 模式，风格同 `onClickSync`；代码遵循 `eslint.config.mjs`（无分号、单引号，Promise 链）。

## 4. 边界 / 幂等 / 并发

| 情形 | 行为 |
|---|---|
| reset 与全量/补偿同步并发 | `progress.running` 拒绝（409），避免删行与写入竞态 |
| reset 与该群在途实时回查并发 | 清完再 `scheduleRealtimePull(conv, 0)`；在途循环按 talker 合并、取 `min(start)`。极端下可能少量重复，dedup 已清故无阻，测试场景可接受 |
| 未放行群 reset | 无 queue 行可删、重拉被 `ingestOne` 闸门 skip → 无害空操作 |
| 群从没入过队 | queue/dedup 反查为空 → 删 0 行；`scheduleRealtimePull(conv, 0)` 从头拉（放行则入队，未放行则 skip） |
| 全量 reset 后水位 | `resetWatermark` 归零、`install_time` 保留 → `runFullSync` 从 0 全量、不被误判首装/重启分流影响 |
| 下游重投 | 预期行为，不特殊处理 |

## 5. 测试（vitest，内存库 + 注桩）

- `QueueStore.deleteByConversation`：只删指定群、跨会话隔离、返回行数。
- `Db.resetConversation`：某群入队若干条（含一条撤回看守）→ reset → 该群 queue 清零 + 对应 dedup 键（`external_id` 与 `revoke:` 变体）全消 + **其他群 queue/dedup 不受影响**。
- `Db.resetChannel`：清空整 channel queue+dedup + 水位/断点归零 + `install_time` 保留。
- `SyncService.resetGroup`：非忙 → 调 `resetConversation` + `scheduleRealtimePull(conv, 0)`（spy 验起点=0）；忙 → `accepted:false` 且不删数据。
- `SyncService.resetAllAndFullSync`：非忙 → 清空 + 触发 `runFullSync`；忙 → 拒绝。
- 端到端重灌：桩 client 返回某群历史 → 首轮入队 → `resetGroup` → dedup 已清 → 重拉**真重新入队**（不被 dedup 挡）、**保留 push_allowed**（重拉后仍放行、消息重新入队而非被闸门 skip）。
- 路由（若有 routes 测试惯例）：`:conversationId` / `reset-all` 命中对应方法，`accepted=false` → 409。

## 6. 未尽事项 / 遗留风险

- **定位为测试工具**：无更重的输入校验/审计，交互靠 `type="danger"` + 二次确认防手滑。若将来要给运维用，需补审计与权限。
- **反查依赖 `external_id = dedup_key` 等值假设**：若将来 adapter 改变 dedup 键派生方式，`resetConversation` 的 dedup 反查将失效，需同步调整。
- **REST 历史保留有限**：全量重拉只能拉到 WeFlow 侧还保留的历史，与现有 `runFullSync` 同一外部约束。
- **reset 与在途回查的少量重复**：见 §4；dedup 已清故不阻塞，测试可接受，不额外加锁。
