# 下游媒体上传（uploadMedia）对接设计 · 二期媒体链路

> 日期：2026-07-09
> 分支：`rewrite/v2`
> 背景：下游 forwarder 文本闭环已打通（queue → `receiveMessage` → ACK 判定 → 重试/熔断/死信/断点）。媒体消息（`has_media=1`）当前**故意不取**、留 pending，等二期媒体链路补发。本设计定义二期链路：forwarder 消费媒体消息 → `uploadMedia` 换 `file_id` → `receiveMessage` 带 `file` 引用，完成「先传媒体、再发消息」两步式转发。

## 1. 范围

**本期做**：把二期媒体链路整条做起来——`uploadMedia` 出站客户端 + forwarder 媒体分支 + `receiveMessage` 信封 `file` 字段，用**灰度总闸**兜住，下游 `file` 通了再放量。

**支持类型**：图片 / 语音 / 动画表情 / **文件**（跳过视频）。

**不做**：视频（需手动点击才下载，字段常缺，本期降级处理）；多媒体数组形态（`file` 本期只发单对象）；媒体二进制加解密/掩码（内部工具，明文本地读取，见 [[internal-tool-simplicity]]）；持久化 `file_id`（靠下游幂等复用，见 D5）。

---

## 2. 现状与缺口

| 维度 | 现状 | 缺口（本期补） |
|------|------|----------------|
| 取件 | `queue.pickStmt` 写死 `has_media = 0`，媒体永不出队 | **加 `pickAnyStmt` + `claimNext(includeMedia)` 闸门** |
| forwarder | 只走 `receiveMessage` 文本路径 | **`processOne` 按 `has_media` 分叉出媒体分支** |
| 下游客户端 | 有 `receiveMessage`/`syncGroups`/`ping` | **加 `uploadMedia`（multipart）** |
| 信封 | `ReceiveEnvelope` 无 `file` | **加可选 `file: { file_id, url? }`** |
| 媒体源 | adapter 只存了 `sourceRef`（可能为 null） | **新增 `mediaSource` 模块，转发时按类型定位本地文件** |
| 配置 | 无媒体相关项 | **加 `fileBaseDir` / `mediaEnabled` / `mediaWaitCapSec`** |
| 审计 | `writeAudit` 写死 `isMedia:0, fileId:null` | **传真实 `isMedia/fileId`（列已存在）** |

## 3. 关键决策摘要

| # | 决策 | 理由 |
|---|------|------|
| D1 | **媒体转发是文本的超集**：复用同一串行 worker、同套 claim/重试/熔断/断点/审计，仅在 `processOne` 按 `has_media` 分叉 | 不新起 worker、不新建表；媒体分支最终仍收敛到一次 `receiveMessage` + 现有 `decideOutcome` |
| D2 | **本地文件读取（fs）取字节**，不走 HTTP | 同机部署（路径均为本机）；文件类本就无 `mediaUrl`、必须读盘，统一一条路径最简；免鉴权/免 HTTP 跳 |
| D3 | **拿不到字节一律「降级发纯文本占位」**（视频 / 等落盘超时 / upload 1002 超大或危险扩展名） | 下游至少收到消息、**不丢时序**；`data.content` 本就是 `[图片]/[视频]/[文件] xxx` 占位，无需改写正文；降级也算 `done` + warn 告警 |
| D4 | **「等落盘」与「下游失败」两种语义彻底分开** | 等落盘用 `next_attempt_at` 轮询、**不加 `attempts`**，以墙钟上限收口；下游失败仍走 `attempts` 3 次死信。否则大文件慢下载会被 3 次误杀 |
| D5 | **不持久化 `file_id`**，重试时重新 `uploadMedia` | 下游按 `channel+rawid+mediaFileName` 幂等复用、返回同一 `file_id`（`duplicate=true`），安全且省一次改表 |
| D6 | **文件完整性用 `size == <totallen>` 判定** | appmsg XML 带权威 `<totallen>`；半下载文件 size 天然不足，不用猜临时文件名/不用 sleep 赌 |
| D7 | **灰度总闸 `mediaEnabled` 默认 `false`** | 下游 `receiveMessage.file` 尚未启用；出厂零行为变化，媒体继续留 pending，通了再置 `true` |

## 4. 媒体源解析（新模块 `server/src/downstream/mediaSource.ts`）

纯逻辑 + `fs` 访问，可单测。签名：

```ts
resolveMediaSource(msg: WeflowMessage, opts: { fileBaseDir?: string }, now: number):
  | { status: 'ready', absPath: string, fileName: string, mediaType: MediaType }
  | { status: 'waiting' }        // 未缓存 / 未落盘 / size != totallen
  | { status: 'unsupported' }    // 视频、无从取字节
```

内部复用 `classifyMedia(msg)`（[mediaType.ts](../../server/src/weflow/mediaType.ts)）分流：

| 类型 | 定位方式 | ready 条件 |
|------|----------|-----------|
| image / voice / emoji | `msg.mediaLocalPath`（WeFlow 缓存 `weflow\cache\api-media\...`） | 字段存在 且 文件存在（size>0）；字段缺 → `waiting` |
| file | `<fileBaseDir>/YYYY-MM/<title>`（微信 `xwechat_files\<wxid>\msg\file\...`） | 文件存在 且 **size == `<totallen>`**；否则 `waiting`；`fileBaseDir` 未配 → `unsupported` |
| video / 其它 | — | `unsupported` |

**文件类元数据从 `msg.rawContent` 的 appmsg XML 解析**（图/语/表情不需要）：
- `<title>` → 文件名（含扩展名，如 `道诡异仙 豪华版 (1).epub`；微信已自带 ` (1)` 去重后缀）
- `<totallen>` → 最终字节数（完整性判定用）
- `<fileext>` / `<md5>` → 兜底命名/校验

**路径容错**：主路径 `YYYY-MM`（从 `createTime` 取，**时区待实测校准**）不命中时，在 `fileBaseDir` 的**当月 + 上月**目录里按「文件名==title 且 size==totallen」扫一遍，容忍月份边界/按下载日期归档的偏差。

---

## 5. 文件类：等待落盘 + 完整性判定

文件与图/语/表情不同——**消息先到、字节后落盘**（用户确认：微信会**自动下载**，无需触发，只需等）。所以文件分支是纯粹的「轮询等落盘」：

1. 计算候选路径 + 从 XML 取 `totallen`。
2. `fs.stat`：不存在 或 `size < totallen` → `waiting`；`size == totallen` → `ready`。
3. `waiting` 且 `now - created_at ≤ mediaWaitCapSec` → 退避轮询（不加 attempts）。
4. `waiting` 且已超墙钟上限 → **降级发纯文本占位**。

> 完整性判定不靠「文件出现即可读」——大文件写盘期间会短暂出现不完整体积，`size == totallen` 是唯一可靠信号。

## 6. 总体数据流 / 状态机

```
claimNext(includeMedia = mediaEnabled)        ← gate 关时只取 has_media=0，行为同现在
  │  has_media=1
  ▼
processOne 媒体分支：JSON.parse(rawJson) → resolveMediaSource
  ├─ unsupported ─────────────────────────────┐
  ├─ waiting & 未超 cap → markMediaWait，return │ (不加 attempts，仅置 next_attempt_at)
  ├─ waiting & 已超 cap ───────────────────────┤
  └─ ready → 读盘 → size>MAX? ─是─────────────┤
              │否                               │
              ▼                                 │ fileRef = null（降级 + warn）
         uploadMedia(bytes, fileName, rawid, mediaType)
              ├─ code1 → fileRef = { file_id, url }
              ├─ 1002  → fileRef = null（降级 + warn，见 D3）
              ├─ 1004/1005/transport → decideOutcome → 退避重试/熔断，return
              └─ 1001  → 鉴权有限重试后死信（框架统一）
  ▼
统一收尾：ack = receiveMessage(event, sessionId, sender, data, file: fileRef ?? 略)
          → decideOutcome(ack) →
              done  → markDone + advanceBreakpoint + writeAudit(isMedia=1, fileId=fileRef?.file_id ?? null)
              retry → markRetry（attempts+1）
              dead  → markDead + dlq 告警
```

**关键点**：媒体分支无论「成功上传」还是「降级」，最终都收敛到**同一次 `receiveMessage` + 同一套 `decideOutcome`**，只差 `file` 带不带。上传只是前置步骤，产出 `fileRef` 或 `null`。

## 7. 配置新增（`shared/src/types/config.ts`）

```ts
interface WeflowConfig {
  // …现有字段…
  /** 文件类媒体本地根目录（微信 xwechat_files\<wxid>\msg\file）；未配置则文件类降级 */
  fileBaseDir?: string
}

interface DownstreamForwarderConfig {
  // …现有 maxAttempts/backoffBaseMs/backoffCapMs…
  /** 灰度总闸：是否消费 has_media=1 的媒体消息（默认 false） */
  mediaEnabled?: boolean
  /** 媒体等落盘墙钟上限（秒，默认 300）；超时降级发纯文本占位 */
  mediaWaitCapSec?: number
}
```

后端默认：`mediaEnabled=false`、`mediaWaitCapSec=300`、`MEDIA_MAX_SIZE=50MB`（常量，与下游对齐，待最终确认）。配置校验边界补进 [shared/src/constants/config.ts](../../shared/src/constants/config.ts)。前端 [ConfigPage.vue](../../web/src/pages/ConfigPage.vue) 增补对应输入项（本设计不展开表单细节）。

## 8. 代码触及面（逐文件）

| 文件 | 改动 |
|------|------|
| `shared/src/types/config.ts` | 加 `fileBaseDir` / `mediaEnabled` / `mediaWaitCapSec` |
| `server/src/db/queue.ts` | 加 `pickAnyStmt`；`claimNext(channelId, now, includeMedia)`；`ClaimedMessage` 加 `hasMedia`；加 `markMediaWait(id, nextAttemptAt, now)`（回 pending、置 next_attempt_at、**不动 attempts**） |
| `server/src/downstream/mediaSource.ts` | **新增**：`resolveMediaSource` + appmsg XML `<title>/<totallen>` 解析 |
| `server/src/downstream/client.ts` | 加 `uploadMedia`（multipart FormData/Blob，超时 120s）；`ReceiveEnvelope.file?`；`DownstreamClient` 接口加 `uploadMedia` |
| `server/src/downstream/forwardPolicy.ts` | 复用现有 `decideOutcome`；如需可加一个 upload 专用薄封装（把 `done` 语义解读为「拿到 file_id」） |

> `uploadMedia` 用 undici `FormData`：`form.append('file', new Blob([bytes]), fileName)` + `rawid/mediaFileName/mediaType`，**不手设 Content-Type**（boundary 自动）。成功判定同 `receiveMessage`：HTTP 200 且 `body.code === 1`；传输层失败抛错、`code!=1` 原样返回交决策。

## 9. 错误码与降级映射

| 来源 | code | 本端行为 |
|------|------|-----------|
| uploadMedia | `1`（含 `duplicate`） | 拿 `file_id/url`，进 receiveMessage |
| uploadMedia | `1002` 超大/危险扩展名 | **降级发纯文本占位**（D3，偏离文档 §7 的"死信"，取不丢时序） |
| uploadMedia | `1004/1005` | 退避重试（`decideOutcome`，attempts+1） |
| uploadMedia | `1001` 鉴权 | 有限重试（≤2）后死信 |
| uploadMedia | transport | 恒退避 + 熔断计数（永不因它进死信） |
| receiveMessage | `1003` 媒体引用无效 | 死信（刚上传即失效属异常，人工排查） |
| receiveMessage | 其余 | 同现有文本决策 |
| 媒体源 | `unsupported`（视频等） | 降级发纯文本占位 |
| 媒体源 | `waiting` 超墙钟上限 | 降级发纯文本占位 |

## 10. 审计与可观测

- `writeAudit` 记 `isMedia=1`、`fileId=fileRef?.file_id ?? null`（降级为 null）；`code` 反映最终 receiveMessage 结果。
- **降级告警**：视频/超时/1002/超大 走 `alert.send({ level:'warn', type:'media_downgrade', … })`，让运维看到「哪条媒体没带文件、退化成占位」。
- forwarder 日志在上传/等落盘节点各记一条 debug（不打含 token 的完整 URL，沿用现有脱敏约定）。

## 12. 灰度与分期

1. **合并即上线，行为零变化**：`mediaEnabled=false` 出厂，媒体继续留 pending。
2. 下游启用 `receiveMessage.file` 后，置 `mediaEnabled=true`，先小流量观察审计里的 media done/降级比例。
3. 稳定后常开。视频 / 多媒体数组形态 / `file_id` 持久化按需再议。

## 13. 待确认 / 实测项

| 项 | 说明 |
|----|------|
| `YYYY-MM` 时区 | 文件目录月份取 `createTime` 的本地时区还是 UTC，需按真实落盘目录校准（含月份边界回退是否够用） |
| 图/语/表情完整性 | 这三类是否也存在「字段已出但文件仍在写」的窗口；若有，补 `length` 字段的 size 校验 |
| `MEDIA_MAX_SIZE` | 下游取 50MB 待最终确认；本端预检阈值与之对齐 |
| `fileBaseDir` 与登录账号 | 路径含登录 wxid（`wxid_xxx_5186`），换账号需改配置；是否需要按当前登录态自动推导 |
| receiveMessage 1003 | 上传成功后 `file_id` 何种情况会失效（OSS 过期？），决定 1003 是否该改可重试 |
